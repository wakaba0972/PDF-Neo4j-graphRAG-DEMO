## 2. 目標與原則

### 目標

1. 提升正確證據被檢索到的機率。
2. 降低不相關或重複證據對回答的干擾。
3. 支援跨頁、實體關係及多輪追問問題。
4. 控制送入 LLM 的證據量、token 成本與回應時間。
5. 以可重複執行的評測數據驗證每項改善。
6. 保留答案來源頁碼，證據不足時明確拒答。

### 實施原則

- 先改善檢索精準度與可衡量性，再增加多跳遍歷等複雜功能。
- 所有檢索結果都必須能回溯至原文 chunk 與 PDF 頁碼。
- 新增行為時同步補充單元測試及整合測試。
- 每個階段完成後，以同一套評測集比較品質、速度與 token 使用量。
- 基本向量檢索保留為基準模式，方便與其他策略 A/B 比較。

## 3. PDF 多模態解析

來源：`feature/multimodal-diagram-parsing`（`f1dfc44`、`027c4e4`），2026-10-17 測試；A1～A5 與暫停／停止已於 `fix/multimodal-parsing-followups` 完成。

**目前流程**：頁面正文區（裁掉上下各 8%）渲染為 PNG → Vision 模型依視覺順序輸出 `text`（原文抄寫）、`table`（Markdown 表格）、`diagram`（圖表文字描述）→ 串成文字 → 依字數切 chunk → 抽取圖譜。圖片本身與圖表在頁面上的位置都**不保存**，檢索與問答只看得到文字描述。Vision 失敗頁改用 PDF 文字層；掃描檔（無文字層）也能經 Vision 辨識。

**測試結果**：單元測試全部通過（423 passed）。以 `EPSON_L485.pdf` 實測第 1、10、20 頁皆解析成功；圖表頁（第 20 頁）多出原本純文字擷取沒有的圖表描述，功能方向正確。

| # | 問題 | 影響 | 做法 | 狀態 |
| --- | --- | --- | --- | --- |
| A1 | 逐頁同步呼叫 Vision API | 每頁 5～10 秒，151 頁約 15～25 分鐘；原本 `get_text()` 不到 1 秒 | 用執行緒池並行處理（例如 8 頁一批），並處理 API 速率限制 | ✅ 預設 8 並行；16 頁由約 2 分鐘降至約 12 秒 |
| A2 | 解析階段沒有進度條 | `extract_pdf()` 與 `add_document_for_ui()` 沒有進度回報，UI 長時間無回應 | 比照 `graph_service.py` 的 `progress_callback`，在 UI 用 `gr.Progress()` 顯示「第 N / 總頁數」 | ✅ |
| A3 | 失敗時靜默回退 | `except Exception` 一律退回純文字擷取且不記錄；API key 錯誤或額度用完時，整份文件不會用到 Vision，使用者也不會發現，且每頁仍先浪費一次請求 | 記錄失敗頁碼與原因並顯示於完成訊息（例如「12 頁改用純文字擷取」）；HTTP 401／403／404 時停止呼叫 Vision | ✅ |
| A4 | 模型名稱寫死 | `VISION_MODEL = "gpt-6-luna"` 不讀 `model_settings.yaml`，切換模型無效，一律呼叫 OpenAI | 新增 Vision 模型用途設定，並與既有模型設定共用 | ✅ 1-1「PDF 解析模型（Vision）」，可停用 |
| A5 | Prompt 限定汽車維修手冊 | 圖表描述強制「由零件A、零件B構成」；非汽車文件（如印表機連線示意圖）描述不自然 | 改為通用文件描述，或讓文件領域可設定 | ✅ 改為通用技術文件 prompt |
| A6 | 每頁都呼叫 Vision | 大份手冊 API 成本高，見下方 token 實測 | 以 PyMuPDF 偵測頁面元素，只對含圖片、向量繪圖或表格的頁面使用 Vision，純文字頁維持 `get_text()`（0 token） | ⬜ 需先以實際手冊確認偵測不會漏掉圖表；可在 UI 提供「全部頁面／僅含圖表頁」選項 |
| A7 | 表格可能被 chunk 切斷 | `chunk_pages()` 依字數切分，大型 Markdown 表格可能從中間切開，後段 chunk 沒有表頭，檢索與圖譜抽取難以理解欄位 | chunk 切分時把表格視為不可分割區塊；表格超過 chunk 大小時按列切分，每段重複表頭 | ⬜ 不花 token，問答品質影響最直接 |
| A8 | 圖片無法裁切、UI 不顯示原圖 | 只保留模型的圖表描述，描述遺漏的細節找不回來；使用者看不到原圖 | 一般圖片用 `page.get_image_info()` 取位置、向量繪圖用 `page.cluster_drawings()` 分群、表格用 `page.find_tables()`（PyMuPDF 1.28.2 皆可用），裁切後存入專案並連到對應的 diagram 描述；或需要時從專案內 PDF 即時渲染來源頁。在 1-1 chunk 預覽與問答檢索來源顯示 | ⬜ 不花 token；向量圖分群準確度需實測。不建議改由 Vision 回傳座標（不準且增加輸出 token） |
| A9 | 解析可暫停／停止 | 長時間解析無法中斷 | 1-1 獨立 `RunControl`；暫停時不送新頁面，停止時立即返回並捨棄該份 PDF | ✅ 實測按停止約 0.1 秒內返回；已送出的請求（最多 8 頁）仍會計費 |

**驗收標準**

- ✅ 151 頁文件解析時間明顯縮短，UI 可看到逐頁進度。
- ✅ Vision 失敗頁數與原因會顯示在解析結果。
- ✅ 可在設定中選擇 Vision 模型。
- ⬜ 以實際文件人工確認非汽車手冊的圖表描述用詞合理。

**Token 實測**（2026-10-17，gpt-6-luna，`EPSON_L485.pdf`，渲染倍率 2.0）

| 頁 | 內容 | 輸入 token | 輸出 token |
| --- | --- | --- | --- |
| 1 | 封面＋法規文字 | 2,248 | 361 |
| 10 | 滿頁注意事項 | 2,248 | 1,292 |
| 20 | 文字＋示意圖 | 2,248 | 487 |
| 60 | 一般頁 | 2,248 | 425 |
| 100 | 一般頁 | 2,248 | 651 |

- 輸入每頁固定約 2,250 token（圖片 token 只取決於解析度），其中約 1,800 為 cached。
- 輸出依頁面字數約 360～1,300 token，平均約 640。
- 整份 151 頁估計：輸入約 34 萬、輸出約 10 萬 token；費用依帳號模型單價換算。
- 輸出 token 大多用於重抄文字層已有的文字，因此 A6 是主要省錢手段；A7、A8 都在本機處理，不增加 token。

## 4. 各項目細節

### P0：評測集與指標 🟡

**已完成**

- 從 PDF 自動生題（含來源頁碼與 chunk），題目集可匯入、編輯、匯出，並集中管理與綁定專案。
- 單一專案與跨專案實驗：多實驗組、回答模型、檢索策略並行比較，AI 判分。
- 人工評測：3-0 分層抽樣與分派、3-1 盲評、4-0 AI／人工結果比較。
- 檢索指標：Evidence Hit Rate、Evidence Recall、Evidence Precision、Evidence F1、Document Hit Rate。

**待完成**

- 從實際 PDF 人工整理 30～50 題固定基準集，每題記錄問題、答案要點、正確來源頁碼／chunk、題型、是否有答案。
- 題型至少涵蓋：單段落、錯誤碼／型號／數值精確查詢、跨頁整合、實體關係／原因影響、無答案問題、多輪追問。
- 補充指標：無答案正確拒答率、平均與 P95 回應時間、每次問答的 context token 數。

### P1：全文與向量混合檢索 ✅

已完成 CJK 全文索引、官方 HybridCypherRetriever 與內建 naive ranker、run ID 隔離，以及 UI 顯示官方混合分數。後續只需以 P0 基準集確認精確詞查詢的 `Recall@K` 不低於基本向量檢索。

### P2：候選去重與重新排序 🟡

**已完成**：共用流程支援停用／詞彙 Reranker／LLM Reranker。

**待完成**

- 向量、全文、圖譜擴展結果先組成候選集合，依 `evidence_id`、來源 chunk 與文字相似度去重。
- 為所有候選計算統一分數，擴展證據不再固定為 `0.0`。
- 檢索來源介面顯示向量、全文、圖譜及最終分數。

建議初始公式（權重需以評測集調整）：

```text
final_score = 0.45 × vector_score + 0.25 × keyword_score
            + 0.20 × graph_score  + 0.10 × source_proximity_score
```

圖譜分數：直接命中實體 > 一跳關係＝關係來源原文 > 同 chunk 擴展 > 兩跳關係；無法回溯原文者不送入回答模型。

**驗收**：擴展證據有可解釋分數、依統一分數排序、重複證據比例下降且答案品質不退步。

### P3：Context token 預算 ⬜

- 新增 `max_context_tokens`，依回答模型 context window 預留 system prompt、問題與歷史、回答輸出空間。
- 依最終排序逐筆加入證據，超過預算即停止；限制單一 chunk 長度，合併相鄰重疊 chunk。
- 原文、實體、關係各設最低與最高比例，避免單一類型占滿。

**驗收**：不會因 Top K 或圖譜擴展超過 context window；問答紀錄包含實際證據數與估算 token 數。

### P4：有方向的圖譜擴展 🟡

**已完成**：Agentic Search（程式查鄰居、LLM 選路，限制跳數與分支）與 Agentic Search 3（LLM 以固定工具搜尋，不接受任意 Cypher）。詳見 [檢索策略擴充指南](檢索策略擴充指南.md)。

**待完成**

- 共用流程的圖譜擴展改為從高分實體出發：命中實體 → 一跳關係 → 鄰接實體 → 關係來源原文 → 統一 rerank → 依 token 預算組裝。
- 依問題類型限制可擴展的關係；預設一跳，比較／原因／影響／路徑題才考慮兩跳。
- 高度數節點降權，限制每個起點的最大關係數與總擴展數。

**驗收**：擴展結果能說明起點、關係與距離；關係型題目正確率高於基本向量檢索；一般事實題不退步。

### P5：多輪問答與問題改寫 ⬜

- 保存最近 3～5 輪問題與回答摘要，納入 token 預算。
- 檢索前將含代名詞或省略的追問改寫為獨立問題，同時保存原始與改寫後問題。
- 新對話或切換文件時清除歷史；使用者可手動清除。

```text
上一題：E01 應該如何處理？
追問：那如果還是沒有恢復呢？
改寫後：依照 E01 的排除步驟處理後，設備仍未恢復時，下一步應如何處理？
```

**驗收**：多輪評測題能正確解析指代；改寫不加入不存在的前提。

### P6：證據充分性判斷與二次檢索 🟡

**已完成**：Agentic 策略在搜尋迴圈中自行決定繼續或停止；回答 prompt 要求證據不足時明確說明。

**待完成**

- 共用流程在第一輪後判斷證據是否充分；不足時抽取關鍵實體、產生同義詞、拆解子問題或改用其他檢索方式。
- 合併兩輪候選後重新去重、排序並套用 token 預算；設定最多輪數。

**驗收**：每次二次檢索有可記錄的觸發原因；無答案題的臆測比例下降；延遲與呼叫次數在上限內。

### P7：依問題類型選擇檢索策略 ⬜

| 問題類型 | 建議策略 |
| --- | --- |
| 錯誤碼、型號、數值 | 混合檢索 |
| 實體定義或說明 | Local GraphRAG |
| 原因、影響、相互關係 | Agentic Search（實體起點＋關係遍歷） |
| 整份文件主題或趨勢 | Community summary／Global Search（見 [Microsoft GraphRAG 與 Neo4j 整合](Microsoft-GraphRAG與Neo4j整合.md)） |
| 多輪追問 | 問題改寫後再檢索 |

- 新增輕量分類器或規則判斷，自動選擇結果顯示於問答紀錄；保留手動指定模式。

**驗收**：分類準確率達門檻；自動模式整體品質高於固定單一策略。

## 6. 測試計畫

- **單元測試**：去重、統一評分、token 預算裁切、問題改寫、二次檢索觸發條件。
- **Neo4j 整合測試**：全文索引、run ID 隔離、一跳關係與來源 chunk 回溯、高度數節點與擴展上限、空資料庫與查詢錯誤處理。
- **UI 測試**：參數傳遞、分項分數顯示、多輪歷史保存與清除、錯誤訊息不清除既有有效狀態。
- **回歸評測**：每階段完成後執行固定評測集，與基本向量檢索及前一版比較；核心指標下降時先找出退步題型。

## 8. 風險與控制

| 風險 | 控制方式 |
| --- | --- |
| Vision 解析耗時與成本過高 | 並行處理、只對含圖表頁使用 Vision、顯示失敗統計 |
| 圖譜擴展帶入大量雜訊 | 限制跳數與每節點關係數，統一 rerank |
| 全文與向量結果重複 | 以 evidence ID、chunk 與文字相似度去重 |
| context 超限 | 強制 token 預算並預留回答空間 |
| 問題改寫產生錯誤前提 | 保存原始問題、限制改寫用途並加入測試 |
| 二次檢索增加延遲與成本 | 觸發門檻、最大輪數與逾時 |
| 建圖抽取品質限制檢索上限 | 追蹤實體／關係抽取準確率，保留原文兜底 |
| 指標改善但體感下降 | 同時檢查離線評測、人工評測與回應時間 |

## 9. 成功條件

- 正確來源的 Evidence Recall／Hit Rate 相較基準提升。
- 關係型與跨頁問題的答案正確率提升，引用頁碼正確可追溯。
- 無答案問題不會因圖譜擴展而增加臆測。
- 問答 context 不超過 token 預算，延遲與成本在可接受範圍內。
- 多輪追問不需使用者反覆補充主詞。
- 各檢索策略能以相同評測集持續比較。
